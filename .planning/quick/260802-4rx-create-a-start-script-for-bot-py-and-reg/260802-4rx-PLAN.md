  <action>
Create `/home/ec2-user/secretary-bot/start_bot.sh` with the Write tool (never a heredoc), containing,
in order:

1. Shebang `#!/usr/bin/env bash`.
2. `set -euo pipefail`.
3. A one-line comment explaining WHY the wrapper exists rather than what it does: systemd's
   `EnvironmentFile=` cannot parse the `export KEY=value` lines in `env`, and copying the secrets
   into a second bare-`KEY=value` file would duplicate credentials on disk.
4. `cd /home/ec2-user/secretary-bot` — absolute, so the script is correct regardless of caller cwd.
5. A guard: if `env` is not a readable file, write a clear diagnostic to stderr naming the missing
   path and `exit 1`. Fail loudly rather than silently starting a bot with no token.
6. Credential load using `set -a`, then `. ./env`, then `set +a`. Source the file directly — it is
   already written as shell `export` statements, so sourcing is exactly what its format is designed
   for. Do NOT use the `export $(grep -v '^#' env | xargs)` form from CLAUDE.md here: `xargs` word-splits
   on whitespace and strips quotes, which silently mangles any future value containing a space, and it
   also feeds a stray bare `export` token as an argument. The `set -a` + source form is equivalent for
   today's values and correct for all future ones.
7. Final line `exec /home/ec2-user/secretary-bot/venv/bin/python3 /home/ec2-user/secretary-bot/bot.py`.
   `exec` is required so the Python process replaces the shell and becomes the unit's `MainPID` —
   without it systemd would track the wrapper shell and lose reliable stop/restart semantics.

The script must contain zero credential values — only the path to `env`.

Then `chmod 755 /home/ec2-user/secretary-bot/start_bot.sh` (owner-write only; group/other must not be
able to modify a script that runs with the bot's secrets).

Do not add `set -x`, `echo`, or any debug tracing — that would print token values into the journal.
  </action>

Perform the cutover in this exact order. Telegram's `getUpdates` is a single-consumer API — if two
pollers overlap, BOTH receive errors and the bot becomes unusable, so the old process must be fully
dead before the new one starts.

Step 1 — locate the manual process. Enumerate candidates with
`ps -eo pid,comm,args --no-headers | awk '$2 ~ /^python/ && /bot\.py/ {print}'`.
Filtering on the `comm` field is mandatory here: a plain `pgrep -f` also matches the agent's own shell
wrapper and reports phantoms. Expect exactly one row (a `python3` whose args reference `bot.py`).

Step 2 — terminate it gracefully. Send a plain `kill <PID>` (SIGTERM). Poll for exit for up to ~10
seconds. Only if it is still alive after that, escalate to `kill -9 <PID>`. Then confirm zero matching
Python processes remain using the same `ps`+`awk` filter. Do not proceed while any remain.

Step 3 — start the managed service: `sudo systemctl start secretary-bot`.

Step 4 — allow roughly 8-10 seconds for Telegram polling to establish, then inspect
`journalctl -u secretary-bot --since "2 minutes ago" --no-pager`. Confirm a successful startup and the
absence of Telegram single-consumer collision errors (a leftover competitor would surface as a 409
from `getUpdates`). If such errors appear, an old poller survived — return to Step 2.

Step 5 — confirm the surviving process is the systemd-owned one by comparing the PID found via
`ps`+`awk` against `systemctl show -p MainPID --value secretary-bot`.

Do NOT delete or truncate `nohup.out`. It holds the historical pre-cutover log and is gitignored;
leave it in place. New logs go to the journal from now on — that is the intended outcome.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `env` file → process environment | Live Telegram and OpenAI credentials cross into the runtime here |
| process → journald | Anything the process writes to stdout/stderr becomes readable via `journalctl` |
| repo working tree → git remote | Any newly added file is a candidate for being committed and pushed |
| local host users → `start_bot.sh` | A script executed by the service with access to the bot's secrets |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-QUICK-01 | Information disclosure | `start_bot.sh` → journald | high | mitigate | Wrapper contains no `set -x`, no `echo` of values, and no credential literals — only the path to `env`. Task 1 verification asserts env loading using `test -n` on variables, never printing them. |
| T-QUICK-02 | Information disclosure | git working tree | high | mitigate | No second env file is created, so secrets are not duplicated. `start_bot.sh` holds no values. `.gitignore` already covers `env`; Task 1 asserts `start_bot.sh` itself is *not* ignored (it is a normal repo file) while leaving `env` ignored. |
| T-QUICK-03 | Tampering | `/home/ec2-user/secretary-bot/start_bot.sh` | medium | mitigate | Installed mode 755, owned by `ec2-user` — group and other cannot write. A world-writable script here would let any local account execute arbitrary code with the bot's credentials. |
| T-QUICK-04 | Elevation of privilege | `/etc/systemd/system/secretary-bot.service` | medium | mitigate | Unit installed root-owned mode 644 via `sudo install -m 0644 -o root -g root`. The service body drops to `User=ec2-user`/`Group=ec2-user`; the bot never runs as root. |
| T-QUICK-05 | Denial of service | Telegram `getUpdates` long poll | high | mitigate | Ordered cutover: the manual poller is terminated and confirmed gone before `systemctl start`. Task 3 verification asserts exactly one process and greps the journal for single-consumer collision errors. |
| T-QUICK-06 | Denial of service | systemd restart loop | medium | mitigate | `Restart=on-failure`+`RestartSec=2` with systemd's default start-limit burst caps a bad-config loop; the wrapper fails fast with a clear stderr diagnostic if `env` is missing. Task 3 asserts `NRestarts` is 0. |
| T-QUICK-07 | Repudiation | log destination change | low | accept | Logs move from `nohup.out` to journald. Accepted and intended: journald adds timestamps and unit attribution, which is strictly better provenance. `nohup.out` is preserved for history. |

No package-manager installs are in scope for this task (no `pip`/`npm`/`cargo` invocation), so no
supply-chain legitimacy checkpoint is required.
</threat_model>
