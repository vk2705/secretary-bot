<objective>
Let the owner read back the exact system prompt the bot is being given for their account, verbatim, with no LLM call and no conversational side effect.

`build_system_prompt(user, chat_id)` is already a pure function of the user dict with no Telegram or network dependency, so the capability itself is nearly free. The work in this plan is entirely about **fidelity and containment**: the bytes the owner reads must be exactly the bytes the model receives, and those bytes — which contain real journal entries, notes and profile memory — must not land anywhere except the owner's own chat.

Purpose: remove the guesswork from every later prompt-affecting phase. Phase 3 rebuilds prompt assembly entirely; this is the instrument that makes that rebuild verifiable.
Output: a working `/debug prompt`, and a test class that pins verbatim fidelity including non-ASCII content.
</objective>

  <action>
Replace the placeholder `prompt` branch in `debug_cmd` with a delegation to a new `async def _debug_prompt(update, context)` placed directly beneath `debug_cmd`.

`_debug_prompt` resolves `chat_id` from `update.effective_chat.id`, loads the user through the existing `get_user(chat_id)` so the dump reflects exactly what a live turn would see including the SQLite preference overlay, then calls `build_system_prompt(user, chat_id)` and holds the result unmodified.

Delivery branches on length against a 4000-character threshold, chosen to sit below Telegram's hard 4096-character message limit with headroom rather than at it. At or below the threshold, reply with the prompt string as the entire message body — nothing prepended, nothing appended, no formatting mode set, no truncation. Above the threshold, follow `export_data`'s pattern exactly: encode the prompt as UTF-8, construct a `BytesIO` over those bytes, set its `name` attribute and pass a matching `filename` of `system_prompt.txt`, and send it with `reply_document`. A short caption naming the character count is permitted on the document path because a caption is transport metadata and is not part of the delivered bytes.

Three containment rules govern this function and are the reason it exists as its own small unit:

First, it must never construct a file handle on the filesystem and must never import or use a temporary-file facility. The `BytesIO` path exists precisely so nothing is written anywhere, tracked or untracked, satisfying the phase's privacy constraint by construction rather than by cleanup.

Second, it must contain no logging statement of any kind. The prompt body carries the user's real journal entries, notes and profile memory; the systemd journal is a durable copy outside git's reach and is out of bounds. The existing tool-call logging inside `chat()` records tool arguments and results, not the system prompt, and that boundary must not move.

Third, it must not reach the conversational path: no `chat()` call, no append to the user's `history`, no `_touch_activity`, no `save_state`. The dump is a read.

Write the tests first as this task's red phase, in a new `TestDebugPrompt` class in `tests/test_bot.py`, covering every case in the `<behavior>` block. For the no-LLM-call assertion, patch `bot.get_llm_client` to return an object whose chat-completions creation method is an `AsyncMock`, and assert that method was never awaited — this is the Wave-0 gap 01-VALIDATION.md flags as having no existing precedent in the suite, so build it as a reusable helper other plans can import. Name that test so it is selected by the `debug_prompt_no_llm_call` substring, and the long-prompt test so it is selected by `debug_prompt_long`, matching 01-VALIDATION.md's Per-Task Verification Map.

To drive the long-prompt case deterministically, seed the isolated test database with enough note and journal rows through the existing `db_add_note` and `db_add_journal` helpers to push the assembled prompt past the threshold, rather than monkeypatching `build_system_prompt` — the point of the test is that the real assembled prompt survives the real delivery path. Include Cyrillic text in at least one seeded note and one seeded journal entry so the encoding case and the length case are exercised together.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram user → `debug_cmd` prompt branch | Only `chat_id` distinguishes the owner from anyone else who guesses the command |
| Assembled prompt → delivery transport | The prompt aggregates journal entries, notes, profile memory and episodic memory — the most sensitive data the bot holds — into one payload |
| Bot process → host log stream | A logging call here would copy that aggregate into the systemd journal, outside git but equally durable |
| Bot process → filesystem | A temporary-file delivery would leave that aggregate on disk, requiring cleanup that could fail |
